# Requirements Document - Workflow Node Conversion

## Introduction
ワークフロー図（ノードとエッジで構成される設計図）を、実行可能なソースコードまたは詳細なスケルトンコードへ変換するための仕組みを定義します。
この機能により、設計者が視覚的に定義したビジネスロジックやアルゴリズムを、手動での書き直しを介さずに各プログラミング言語の実装へ反映させることが可能になります。

## Alignment with Product Vision
- **ワークフローのコード変換**: 視覚的な設計から実装への自動変換を実現し、開発スピードを向上させるという `product.md` のゴールに直結します。
- **分離された責務**: エディタがデータモデル（TypeModel）を構築し、各言語ビルダーがコード生成を担当することで、多言語対応の拡張性を維持します。

## Requirements

### Requirement 1: 言語中立なデータモデル（TypeModel）の定義
**User Story:** 開発者として、図面エディタが特定の言語に依存しない形式でロジック構造を出力できるようにしたい。そうすることで、一度の設計で複数の言語（Rust, TypeScript等）への出力を容易にしたい。

#### Acceptance Criteria
1. Webview 側のエディタは、ノード間の接続（シーケンス、分岐、ループ、合流）を論理的な構造として保持する `TypeModel` を生成しなければならない。
2. `TypeModel` は、抽象構文木 (AST) に準じた、制御構造（If-Else, For/While, Try-Catch 等）を表現可能な形式でなければならない。
3. ノード内に記述された擬似コードまたは変数の定義情報を、構造化されたデータとして保持しなければならない。

### Requirement 2: 各言語 Builder への変換インターフェース
**User Story:** 言語ビルダーの実装者として、エディタから渡された `TypeModel` を受け取り、自言語の構文へ変換するための明確な契約（インターフェース）が欲しい。

#### Acceptance Criteria
1. `CodeBuilder` 抽象クラスまたはインターフェースは、`TypeModel` を入力として受け取る `buildWorkflow(model: TypeModel)` メソッド（または類似の仕組み）を持たなければならない。
2. 制御構造（分岐ノード -> `if`, 繰り返しノード -> `for` 等）を、各言語の慣習（命名規則、波括弧のスタイル等）に沿って出力しなければならない。

### Requirement 3: 基本的な制御フロー・ノードのサポート
**User Story:** 利用者として、標準的なプログラムの制御構造をワークフロー図で表現し、それが正しくコード化されることを期待する。

#### Acceptance Criteria
1. **開始/終了ノード**: 関数の開始と復帰（Return）を生成しなければならない。
2. **アクションノード**: 代入や関数呼び出しなどの 1 ステートメントを生成しなければならない。
3. **条件分岐（判定）ノード**: `if-else` または `switch` 構造を生成しなければならない。
4. **繰り返し（ループ）ノード**: `for`, `while` などのループ構造を生成しなければならない。

## Non-Functional Requirements

### Code Architecture and Modularity
- **責務の分離**: エディタ（Webview）は「図面の正規化と TypeModel 構築」を行い、拡張機能側（Extension Host）は「TypeModel のパースとコード生成」を行う。
- **拡張性**: 新しいノードタイプや新しい言語ビルダーを、既存のコードへの影響を最小限にして追加できるように、プラグイン的な構成を目指す。

### Performance
- 何百ものノードを持つ大規模なワークフローであっても、数秒以内にコード生成を完了しなければならない。

### Usability
- コード生成時に、どのノードがどのコード行に対応するかのヒント（コメント等）を付加し、生成後の手修正を容易にする。
